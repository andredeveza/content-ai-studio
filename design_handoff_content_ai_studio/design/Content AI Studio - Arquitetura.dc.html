Documento de Arquitetura · v1.0 · Pré-implementação

Content AI Studio

Estúdio de conteúdo com IA. O usuário informa um tema — o sistema pesquisa, estrutura, escreve, ilustra, renderiza e publica. Arquitetura orientada a domínio, provedores intercambiáveis, identidade visual desacoplada do layout.

Next.js 15 · React 19 TypeScript estrito Supabase Clean Architecture HTML + Puppeteer
01 — PRINCÍPIOS

Regras que não se negociam

Cada decisão abaixo existe para que o sistema cresça sem reescrita. Elas restringem o código de propósito.

Dependências apontam para dentro
Domain não conhece Next.js, Supabase ou provedor de IA. Infra implementa interfaces declaradas pelo domínio.
Todo provedor é substituível
IA, storage, fila e publicação são plugins registrados por configuração. Adicionar um não altera nenhum outro arquivo.
Estrutura ≠ identidade
Template define grid, áreas e proporções. Brand Kit define cor, fonte, logo e estilo. Nunca se misturam.
Renderização é HTML
Slides são DOM real, estilizado por CSS custom properties. Puppeteer apenas fotografa. Zero Canvas.
Gratuito primeiro
Free tier maduro tem prioridade. O custo entra como fallback, nunca como dependência estrutural.
Toda geração é auditável
Prompt, provedor, modelo, tokens, custo, latência e resultado ficam em ai_logs.

03 — AI GATEWAY

Uma porta para toda IA

Nenhum componente, action ou serviço fala com uma API de IA. Todos falam com o Gateway, que resolve provedor, aplica fallback, registra log e normaliza a resposta.

interface AIProvider { id: ProviderId capabilities: Capability[] generateText(i: TextInput): Promise<TextOutput> generateImage(i: ImageInput): Promise<ImageOutput> analyzeImage(i: VisionInput): Promise<VisionOutput> embed(i: EmbedInput): Promise<EmbedOutput> healthcheck(): Promise<boolean> } class AIGateway { constructor( registry: ProviderRegistry, policy: FallbackPolicy, logger: AILogger, limiter: RateLimiter, ) {} run<T>(task: Task): Promise<Result<T>> }
TEXTO
Kimi → OpenRouter → Gemini
IMAGEM
Hugging Face → Replicate → Fal.ai
VISÃO
Gemini → Qwen VL → Florence
Política de fallback
Timeout, erro 5xx, quota ou resposta inválida no schema disparam o próximo provedor. Circuit breaker por provedor, com reabertura progressiva. Ordem definida em config/ai.ts, sobrescrevível por cliente.
04 — LAYOUT BLUEPRINT

Template é molde. Brand Kit é aparência.

O Figma enviado é lido como blueprint estrutural: extraímos grid, áreas, hierarquia, proporções e margens — nunca cor, fonte, logo ou ilustração. O resultado é um Template JSON + HTML que qualquer cliente veste com o próprio Brand Kit.

Template — o que ele guarda
Grid, colunas, gutters e safe area
Slots: header · media · body · footer · cta
Proporções e posição relativa dos blocos
Escala tipográfica em múltiplos (não em px absolutos)
Regras de overflow e reflow por quantidade de texto
Variantes de slide: capa · conteúdo · lista · fechamento
Brand Kit — o que ele injeta
Paleta como CSS custom properties
Famílias e pesos tipográficos
Logo, marca d'água e posicionamento
Estilo gráfico: raio, sombra, traço, textura
Estilo de imagem e prompt base do cliente
CTA, handles, tom de voz e persona
Figma / PNG / PDF → VisionAnalyzer → LayoutBlueprint (JSON) → TemplateCompiler → Template + BrandKit ↓ HTML + CSS vars → Puppeteer → PNG 1080×1350

08 — DESIGN SYSTEM

Interface do produto

Duas camadas visuais separadas: o chrome do produto (neutro, denso, silencioso) e o canvas do cliente (100% Brand Kit). O produto nunca colore o conteúdo do cliente.

Tokens
Escala de espaço 4/8 · raio 8-16 · 1 acento · 6 níveis de superfície · tipografia em 6 degraus · sombra apenas em overlay.
Primitivos
shadcn como base: Button, Input, Select, Dialog, Sheet, Popover, Tabs, Toast, Command, Tooltip, Skeleton.
Compostos
ThemeInput, ClientSwitcher, BrandKitCard, SlideCanvas, SlideRail, InspectorPanel, ProgressStepper, CalendarBoard.
Movimento
Framer Motion, 120–200ms, ease-out. Só entra animação que comunica estado: progresso, reordenar, abrir inspector.
Densidade
Editor denso e utilitário; onboarding e gerador arejados. Comando ⌘K como navegação primária.
Estados
Todo componente define loading, vazio, erro e parcial — geração por IA falha e o layout precisa suportar.
09 — SEGURANÇA

Limites e controles

Chaves só no servidor. Variáveis de ambiente + secret manager; nenhuma chamada de IA a partir do browser.
RLS em tudo. Isolamento por org_id na própria base, não apenas na aplicação.
Rate limit em camadas. Por usuário, por org e por provedor, com orçamento mensal de custo de IA.
Tokens OAuth cifrados. Credenciais de canais em vault, com rotação e revogação por cliente.
Validação de saída. Toda resposta de IA passa por schema Zod antes de tocar o domínio.
Auditoria. Logs estruturados de ação, geração e publicação, com retenção definida.

11 — APROVAÇÃO

O que preciso decidido antes do código

01
Arquivo do Figma. Ainda não recebi o blueprint. Sem ele não consigo derivar os primeiros Templates — envie o .fig ou o link.
02
Fila. Trigger.dev (grátis para começar, menos infra) ou BullMQ + Redis (controle total, exige host). O adapter cobre os dois — preciso do padrão.
03
Puppeteer em produção. Vercel não roda Chromium pesado bem; sugiro worker separado (Railway/Fly) ou browserless. Confirmar hospedagem.
04
Publicação direta vs. agregador. Instagram Graph API exige conta business + revisão do app. Postiz/Metricool encurtam o caminho no MVP.
05
Escopo do MVP. Proponho fechar em P0 + P1 (~11 semanas) com Instagram apenas. Calendário e demais canais na v1.1.
06
Conteúdo de saúde. Os exemplos são clínicos — precisamos definir camada de revisão/compliance antes de publicar automaticamente.
